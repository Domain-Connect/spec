# Issue #216 — Conformance check against draft-ietf-opsawg-rfc5706bis-08

- **Checked document:** [draft-ietf-dconn-domainconnect-04.adoc](../draft-ietf-dconn-domainconnect-04.adoc) (state of branch `pawel-kow/issue216`, 2026-10-07)
- **Re-checked (Status -05):** working state of -05 on branch `pawel-kow/issue216` at commit `b1d140b` ("WIP: Consider BCP on Operational Considerations"), 2026-10-07
- **Reference BCP:** [draft-ietf-opsawg-rfc5706bis-08](https://www.ietf.org/archive/id/draft-ietf-opsawg-rfc5706bis-08.html), "Guidelines for Considering Operations and Management in IETF Specifications" (obsoletes RFC 5706, updates RFC 2360)
- **Issue:** <https://github.com/Domain-Connect/spec/issues/216>. OPSAWG asks the WG to add an "Operational Considerations" section before the draft leaves the WG.

---

## TL;DR

**Overall:** The draft has **no "Operational Considerations" section**, so it fails the one hard requirement in the BCP (§3.1, MUST). Much of the operational material already exists, but it is spread across the body: the deployment considerations for `_domainconnect`, verification of changes, versioning and extensibility, TTL policy, conflict handling, atomic application, discovery hardening and template onboarding. Most of the work is therefore one new section that **summarizes and points to** that text, plus explicit **"not applicable, because …"** statements for the network-management topics (YANG, MTU, OAM, counters). A small number of **real content gaps** also need new text.

### TODO list (priority order)

**A. Mandatory (blocking for IESG / OpsDir)**

1. **Add a top-level section named "Operational Considerations"** (BCP §3.1, MUST). Place it **immediately before "Security Considerations"** (BCP §3.3): between the "Template Application" chapter ([L2269](../draft-ietf-dconn-domainconnect-04.adoc#L2269)–[L2404](../draft-ietf-dconn-domainconnect-04.adoc#L2404)) and [Security Considerations (L2407)](../draft-ietf-dconn-domainconnect-04.adoc#L2407).
2. In that section, **cover every BCP topic**. For each topic, either summarize the existing text with a cross-reference, or give a one-line reason why it does not apply (BCP §3.1). Do **not** use the §3.2 "no new requirements" boilerplate, because the protocol does introduce operational considerations.
3. **State the management model explicitly** (BCP §1.2, §5, §5.1). Template onboarding, template lifecycle, DNS Provider local policy and applied-template state are all managed through **proprietary interfaces** (onboarding process, control panels). No standardized management protocol or YANG/Information Model is defined, and this is a deliberate decision. Give the rationale.

**B. Content gaps that need new text (not just pointers)**

4. **Migration from DC-SPEC deployments** (BCP §4.2). About 20 DNS Providers and 490+ templates already run on DC-SPEC v2.x. Describe coexistence and what existing operators have to change to conform: stricter `_domainconnect` validation, signing and canonicalization rules, error-response format, removal of the async flow, deprecated `shared`/`warnPhishing` flags, `templateSpecVersion` and `crit`. The pieces are in the draft today, but no migration narrative exists.
5. **Overload protection for the DNS Provider's public end-points** (BCP §4.4, §5.4). The Settings and Query Supported Template end-points are unauthenticated. Add rate-limiting guidance, and extend the HTTP status tables (only 2xx and 404 today) with at least 429 (with `Retry-After`) and 5xx semantics, or point to RFC 9110.
6. **Defaults for retry, backoff and bounds** (BCP §4.1, §4.4). "Appropriate intervals … until … a timeout" ([L2103](../draft-ietf-dconn-domainconnect-04.adoc#L2103)) and "MUST bound the discovery request" ([L2431](../draft-ietf-dconn-domainconnect-04.adoc#L2431)) give no default values or rationale. Suggest conservative defaults (e.g. exponential backoff with a cap, a maximum verification window, a maximum settings response size) and explain why they were chosen. Verification polling against authoritative servers is a load concern.
7. **Scale limits** (BCP §4.4, §5.7.1). Nothing bounds the number of records per template, the apply URL length (browsers and intermediaries limit URLs, and signed URLs with many `properties` can get long), the number of public-key TXT fragments, or the number of `_domainconnect` records a Service Provider iterates over. Define the expected behavior when a limit is exceeded.
8. **Key lifecycle** (BCP §4.1 crypto example, §5.8). Rotation is only implied: "publish each key on a different host name" ([L1291](../draft-ietf-dconn-domainconnect-04.adoc#L1291)). Add operational guidance on key rollover (overlap period, TTL of key records), revocation or withdrawal after compromise, and whether a DNS Provider may cache key records. Explain the `RS256`/`x509` defaults and say they are expected to change over time (algorithm agility through `a=`).
9. **Audit logging and security operations** (BCP §4.5, §5.8). Recommend that DNS Providers log each apply event: template id and version, parameters, signing key, authenticated user, time, conflicts resolved and outcome. This supports incident response, for example after a phishing-driven change. Point out that these logs contain privacy-sensitive data. Name useful attack indicators, such as signature-verification failures and repeated unsigned applies of the same template with varying variables.
10. **Dependencies on other protocols** (BCP §4.3). Make the HTTPS/TLS dependency explicit (server authentication per RFC 9110 / RFC 9525). The draft currently says only "scheme `https`". State the WG's position on DNSSEC for `_domainconnect` and for public-key TXT records.
11. **Template and instance lifecycle** (BCP §5, §5.4.4). Say how a template is updated, deprecated or withdrawn by a DNS Provider (a fault-isolation tool, e.g. after a compromised Service Provider), and how a user or Service Provider disconnects an applied service. If this is deliberately out of scope, say so.

**C. Small items (a sentence or two each, inside the new section)**

12. Explain why `error_description` is RECOMMENDED in English (developer-facing, RFC 6749 ASCII restriction, machine-readable `error` code carried with it), and why display strings carry no language tag (BCP §4.7).
13. Mention that the Settings End-Point can serve as a liveness and health probe, and that Query Supported Template can show the deployed template `version` for troubleshooting (BCP §4.6, §5.4.1).
14. Summarize in one place the DNS Provider local policies an operator configures: TTL min/max/enumeration, supported record types, SPF `all` qualifier, whether template state is tracked, Generic/NS support, phishing-warning presentation (BCP §5.5).
15. Add short "not applicable" statements for: YANG and Information Models (§5.3, §5.3.2), MTU (§4.4), OAM traffic (§4.4), protocol counters (§5.7.1–5.7.3), accounting (§5.6, or point to usage statistics as an implementation matter) and AI tooling (§6.1). For AI tooling, note that the user-consent model rules out unattended agents and that the public query end-points are covered by item 5.
16. Name existing tooling in **permanent** text, not only in the *Implementation Status* section, which is `removeInRFC` (BCP §6): standard DNS tools (e.g. `dig`) for verification, plus the open-source libraries as informative references.
17. Add a Change History bullet for the next revision, e.g. "Added <<operational-considerations,format=title>>, …".

## Legend

- **Level:** BCP 14 keywords appear **only in §3** of the BCP (see BCP §2). Everything outside §3 is lowercase guidance, shown here as *should (guidance)*, *must (guidance)* and so on. Those items are not normative, but OpsDir reviewers will use them (and the Appendix A checklist) to judge the section.
- **Status -04 / Status -05:** -04 is the state of the released -04 text. -05 is the state after commit `b1d140b`; its line links point to the current file on the branch, which still has the -04 file name.
- **Status symbols:** ✅ fulfilled · 🟡 partially fulfilled · ❌ not fulfilled · ➖ not applicable (still needs a one-line statement in the new section, per BCP §3.1)
- **DC ref** (and the links in *Justification*): line numbers refer to the -04 state of [draft-ietf-dconn-domainconnect-04.adoc](../draft-ietf-dconn-domainconnect-04.adoc).
